# Dentiva Pro — Decision Log

Each entry: context → decision → rationale → consequences. Decisions are never silently changed; superseding a decision adds a new entry.

| ID | Decision | Rationale & Consequences |
|---|---|---|
| AD-001 | **Stack: Electron 44 + React 19 + TypeScript 5.9 + better-sqlite3 13 (SQLite)** | Evaluated Tauri 2, .NET 8 WPF, Qt 6/PySide6 (see `ARCHITECTURE.md` §Alternatives). The single hardest requirement set is printing: Windows printers, print preview, paper profiles (A4/A5/thermal), PDF output, and Bengali Unicode shaping. Chromium's print/PDF engine solves all of these natively; every alternative required custom text-shaping + PDF libraries. Electron also builds NSIS installers cleanly on GitHub Actions `windows-latest`. Consequence: installer ~90–120 MB (acceptable for desktop), RAM ~250–400 MB. |
| AD-002 | **Database: SQLite via better-sqlite3** | Synchronous, transactional, mature, WAL mode, foreign keys, triggers. Rejected `node:sqlite` (experimental in pinned runtimes), SQL.js/WASM (manual persistence, weak transactions), JSON/flat files (spec prohibits), localStorage (prohibited). |
| AD-003 | **Money stored as INTEGER paisa (1 BDT = 100 paisa)** | Deterministic integer arithmetic for all totals, payments, change; no floating-point rounding. Formatting to `৳` happens only at display time. Conversion boundary validated with zod (2-decimal input max). |
| AD-004 | **Timestamps: system times stored as UTC ISO-8601 TEXT; business dates stored as local `YYYY-MM-DD` TEXT** | Unambiguous storage; business dates (visit date, invoice date) are clinic-local dates by nature. Default display timezone Asia/Dhaka (configurable). dayjs used in renderer with a single formatting utility. |
| AD-005 | **Password hashing: Node `crypto.scrypt` (N=16384, r=8, p=1, 64-byte key, 16-byte random salt)** | Node built-in — no native dependency; memory-hard; parameters stored with the hash for future upgrades. Plaintext never stored/logged. Account lockout: 5 consecutive failures → 15-minute lock (audited). |
| AD-006 | **Activation: offline one-time code verified against a scrypt-derived verifier constant embedded in source. The plaintext code appears nowhere in the repo, docs, bundle, DB, or logs.** | Honest limitation (documented in `SECURITY_MODEL.md`): a purely offline fixed-code system can never be made unbreakable against a determined reverse engineer with full local access. Mitigations: derived representation (scrypt, constant-time compare), no plaintext exposure, activation state audited, verification logic isolated, input hardening. This matches the spec's own requirement to document this limitation. |
| AD-007 | **All DB access in the Electron main process; renderer has zero direct DB/file access. Every IPC call carries a session token; the service layer enforces RBAC before touching data.** | UI hiding is never the authorization mechanism. A compromised renderer still cannot read/write data it lacks permission for. Response envelope `{ok, data} \| {ok:false, code, message}` for structured errors. |
| AD-008 | **Auto-lock implemented with `powerMonitor.getSystemIdleTime()`** | System-wide idle detection without renderer overhead. Locked sessions reject every IPC call except `auth.unlock`; unlock re-authenticates. Options: 5/10/15/30 min or Never. |
| AD-009 | **Accounting model: single-entry cashbook (income/expense transactions with categories), not double-entry ledger** | Spec §46 explicitly permits documenting a simpler model. Clinics in the target market need cash in/out, category totals and summaries. Income entries are auto-created (and reversed on void) for invoice payments; manual entries cover other income/expenses. Limitation: no balance sheet/trial balance — documented in-product (About/Settings) and here. |
| AD-010 | **Financial documents use void, not delete, as the primary reversal flow. Hard delete of paid invoices/payments is blocked by integrity rules.** | Preserves auditability and financial history (spec §76). `invoice.delete` / `payment.delete` permissions exist for owner-level correction of *unpaid/unreferenced* documents only; everything else is voided with audit. |
| AD-011 | **Deletion policy: soft delete (archive) default for patients; permanent patient delete only when no clinical/financial records exist, else blocked.** | Prevents orphaned financial/clinical history (spec §64, §75). "Delete business data" and "factory reset" are separate, typed-confirmation, pre-backup operations requiring `business.delete`. |
| AD-012 | **Dental chart: FDI notation default (Universal optional in settings); adult (11–48) and pediatric (51–85) dentitions; per-tooth condition entries with full history; current state = latest entry per tooth** | FDI is the standard used in Bangladesh. All chart changes persist and are visit/author-associated (spec §26–27). |
| AD-013 | **Print pipeline: renderer composes semantic print HTML; main process renders it in a hidden BrowserWindow; `printToPDF` output is the canonical preview (shown via the app's secure protocol in an iframe using Chromium's PDF viewer); hardware printing uses `webContents.print()`; Save-as-PDF saves the same canonical PDF.** | Preview fidelity = exactly what prints. Paper profiles (A4, A5, Letter, thermal 80/58 mm, custom) drive both `@page` CSS and PDF page size in µm. Bengali shaping handled by Chromium + bundled Noto Sans Bengali. Thermal continuous-length: PDF preview uses a fixed page height; direct printing delegates paper handling to the Windows driver (documented limitation, spec §125). |
| AD-014 | **Bundled fonts (Noto Sans Bengali, SIL OFL 1.1) instead of relying on Windows fonts** | Guarantees identical Bengali rendering on every machine; license permits commercial bundling with notice (notice shipped in About → Third-Party Notices + font directory). UI falls back to Segoe UI/system-ui for Latin. |
| AD-015 | **Installer: electron-builder NSIS, per-user install, `deleteAppDataOnUninstall: false`** | Per-user needs no admin rights (typical clinic PCs). Patient data is *not* destroyed on uninstall — deliberate medical-data-safety decision, documented in installer & README; a "Factory reset" exists in Settings for explicit data destruction. |
| AD-016 | **UI language: professional English only; all user-entered content supports Bengali Unicode** | Spec mandates professional English interface; a half-translated UI would violate quality rules. No fake language selector shipped. |
| AD-017 | **Renderer state: Zustand stores + React Router (MemoryRouter); no server-side session assumptions** | Small, typed, testable. Deep-link navigation for notifications handled via an internal nav bus. |
| AD-018 | **Testing: Vitest unit + integration (services against real SQLite in temp dirs) run on Linux dev box and Windows CI; Playwright-core drives the real Electron app for E2E smoke (boot, activate, setup, login, core flow) on windows-latest** | The service layer runs unmodified inside tests (dependency-injected context), so business rules, RBAC, and financial integrity are testable without Electron. Physical printing/clean-machine steps beyond CI capability are honestly documented as externally required. |
| AD-019 | **CI: GitHub Actions — `verify` job (typecheck, lint, unit+integration tests) on windows-latest AND ubuntu; `build` job (NSIS installer) on windows-latest; release workflow attaches the validated installer to a GitHub Release.** | Windows runners provide genuine Windows-path/ABI validation and the installer build. No paid external services. |
| AD-020 | **Search: indexed `LIKE` queries with bounded result windows; FTS5 deferred (revisit only if stress tests show need)** | Stress tests with generated datasets (see `TEST_PLAN.md` results) must demonstrate acceptable latency at target scale; decision revisited with evidence, not speculation. |
| AD-021 | **Audit log: written by the service layer for every state change with old/new value JSON; viewer permission `audit.view`; no delete path in any shipped UI** | Defense in depth: app-level protection; SQLite file itself remains accessible to the OS user (documented in `SECURITY_MODEL.md` — offline desktop reality). |
| AD-022 | **Attachments: stored under `userData/attachments/<patientId>/<uuid>.<ext>`; server-generated names only; type/size validation; SHA-256 checksum; served/opened through a validated secure protocol or `shell.openPath`** | Prevents path traversal and filename trust issues (spec §72, §78). |
| AD-023 | **Queue tokens: per-day sequence, stored transactionally; queue states: waiting → called → in-treatment → billing → finished (+ cancelled)** | Persistent, unambiguous daily tokens (spec §30). |
| AD-024 | **Appointment reschedule = new appointment linked to original (`source_appointment_id`), original marked `Rescheduled`** | Preserves history (spec §29). |
| AD-025 | **Invoice/patient/prescription numbering: configurable prefix + transactionally allocated sequence stored in settings** | No collisions, no fake numbers; historical documents keep their numbers. |
| AD-026 | **Overpayment blocked by default** (`payments.allow_overpay` setting can permit credit balance) | Safe default financial rule (spec §112), explicitly documented. |
| AD-027 | **Settings storage: typed `settings` key/value table (JSON values) + structured tables for clinic, dentists, users, roles** | Single migration path, audited updates, no config-file drift. |
| AD-028 | **Logs: local rotating log files with redaction (no passwords, no activation input, no patient data); user can open the log folder from Settings → Advanced** | Diagnosability without privacy liability (spec §98–99). |
| AD-029 | **No telemetry, no auto-update, no outbound network calls at runtime** | Offline product requirement; network permission not requested. |
| AD-030 | **Product scope frozen at 1.0.0**; no "coming soon" or "v2" placeholders anywhere in the product | Spec §121. Unfinished features are not shipped; anything visible is functional. |
| AD-031 | **Print documents use SYSTEM fonts (Noto Sans Bengali if installed → Windows' bundled Nirmala UI → sans-serif), not @font-face webfonts; the app UI keeps the bundled WOFF2 webfonts for display.** | Differential CI diagnostics (print-geometry suite, runs 36722132504/36723879956/36726128680) proved Electron 44 (Chromium 152) cannot print any page whose glyphs come from a webfont — the print compositor rejects the serialized page ("CompositePages: Page reading failed", printToPDF rejects with "Printing failed"), regardless of WOFF2 vs TTF and of protocol vs data-URL delivery; the packaged Windows app's invoice print produced no PDF the same way. System-font pages print correctly on both platforms. Windows 8.1+ ships Nirmala UI with full Bengali support, so printed Bengali remains professional and consistent on every target machine; the print-geometry CI runner installs the bundled Noto TTF to exercise the same path. Revisit when Electron/Chromium fixes the compositor regression (tracked in PRINT_SPECIFICATION.md). |
